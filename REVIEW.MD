# План исправлений по результатам код-ревью

Дата ревью: 2026-08-31. Объём: все пакеты (`ant`, `easy`, `fs`, `devices`,
`anttest`, `examples`), ~9,4k строк. Проверки: `go vet` — чисто,
`staticcheck` — 2 замечания (U1000), `go test -race ./...` — зелёно.

Фокус ревью: безопасность (данные, приходящие по радиоканалу и от
USB-устройства) и соответствие лучшим практикам Go.

Главный вывод: кодовая база зрелая (граничные проверки в парсере фреймов,
ошибки вместо паник, корректная синхронизация USB-драйвера), но есть
несколько уязвимостей класса «удалённый DoS»: crafted-пакеты от RF-пира
(сетевые ключи ANT+/ANT-FS публичны и зашиты в код) могут вызвать панику
в горутине `node.Run` и уронить весь процесс.

## P0 — паники/DoS на внешних данных (приоритетные)

### 1. `fs/manager.go:183` — паника на коротком beacon

**Проблема:** `onData` проверяет только `len(data) == 0`, затем вызывает
`ParseBeacon(data[:8])`. Сам `ParseBeacon` длину проверяет, но срез
`data[:8]` паникует раньше вызова при `1 ≤ len(data) < 8`. `onData`
подключён к `ch.OnBurstData` — burst-payload произвольной длины
контролируется RF-пиром.

**Исправление:** проверять `len(data) >= 8` до среза (или передавать
`data` целиком в `ParseBeacon`, у которого уже есть проверка).

### 2. `devices/common.go` — два места в `baseDevice.onData`

**Проблема (строки 376–379):** при `len(data) > 8` читаются
`data[9]..data[12]` — паника при длине 9–12 (нужно `>= 13`).

**Проблема (строки 414–470):** общие страницы 80–83 читают
`data[2]..data[7]` без проверки `len(data) >= 8`. Короткий burst с
первым байтом `80` → паника на `data[3]`.

**Исправление:** в extended-блоке требовать `len(data) >= 13`; перед
разбором common-страниц требовать `len(data) >= 8`. Профильные парсеры
проверки уже имеют — привести общий диспетчер к тому же уровню.

### 3. `devices/scanner.go:64–69` — extended-поля без проверки длины

**Проблема:** `if len(data) <= 8 { return }`, затем чтение
`data[9]..data[12]` — паника при длине 9–12.

**Исправление:** заменить условие на `len(data) < 13`.

### 4. `fs/manager.go:401–413` (`Download`) — переполнение uint32 и OOM

**Проблема:** `dr.Offset`, `dr.Remaining`, `dr.Size` контролируются
устройством. `total := dr.Offset + remaining` переполняется (uint32) →
паника на `data[dr.Offset:total]`; `make([]byte, total)` до ~4 ГБ на один
ответ → OOM.

**Исправление:** промежуточные суммы считать в uint64; валидировать
`Offset ≤ ожидаемое смещение`, `Offset + Remaining ≤ Size`; ограничить
максимальный суммарный размер файла разумной константой.

### 5. `fs/manager.go:459–465` (`Upload`) — device-controlled смещения

**Проблема:** `ur.LastDataOffset > len(data)` → паника на срезе;
`offset + maxBlock` переполняется; `maxBlock == 0` → бесконечный цикл
(прогресс не двигается при ответах OK устройства).

**Исправление:** до среза проверять `offset ≤ len(data)` и
`maxBlock > 0`; сумму считать в uint64.

### 6. Страховка от паник в цикле диспетчеризации (опционально, после 1–5)

**Проблема:** паника в горутине `Node.Run` убивает весь процесс;
пользователь библиотеки не может защититься сам.

**Исправление:** рассмотреть `recover()` вокруг вызова пользовательских
callback в `easy/node.go` `Run` (с логированием) — как второй рубеж
после точечных проверок, не вместо них.

## P1 — конкурентность и жизненный цикл

### 8. `ant/driver_serial.go` — data race на `s.port`

**Проблема:** `Open`/`Close`/`Read`/`Write` обращаются к `s.port` без
мьютекса. `Core.Stop()` вызывает `Close()` (обнуляет `s.port`), пока
reader-горутина в `Read` — гарантированный конкурентный доступ, прямо
предусмотренный контрактом `Driver`. Возможны race и паника на
nil-интерфейсе.

**Исправление:** добавить `sync.Mutex` по образцу `usbDriver`
(захватывать локальную ссылку на `port` под блокировкой перед I/O).

### 9. `ant/node.go:137–146` — busy-spin reader'а при отказе драйвера

**Проблема:** при постоянной ошибке `Read` (стик извлечён — libusb
возвращает ошибку мгновенно) цикл крутится на 100% CPU без backoff и
без сигнала вызывающему. Подтверждено TODO (#51/#122).

**Исправление:** счётчик последовательных ошибок + backoff
(например, экспоненциальный до ~1 с) либо остановка core с ошибкой
наружу. Заодно убрать дублирующую проверку `!c.running.Load()`
(строки 139 и 142).

### 10. `fs/manager.go:155–166` — deadlock в `NewApplication` при ошибке `SetupChannel`

**Проблема:** при ошибке `SetupChannel` вызывается `app.Stop()`, который
ждёт `<-a.runDone`, но горутина, закрывающая `runDone`, стартует ниже
по коду. `NewApplication` зависает навсегда вместо возврата ошибки.

**Исправление:** запускать run-горутину до вызова `SetupChannel`, либо
в `Stop` не ждать `runDone`, если run loop не стартовал (флаг/
`sync.Once`).

## P2 — корректность протокола и API

### 11. `ant/message.go:259` — молчаливая усечка длины фрейма

**Проблема:** `byte(len(m.Data))` при payload > 255 оборачивается по
модулю 256 → malformed-фрейм. `SendBurstTransferPacket` длину не
проверяет; в `fs.Upload` размер блока приходит от устройства (связка с
находкой 5).

**Исправление:** валидировать длину payload (≤ 255) в `Encode` (вернуть
ошибку — потребует смены сигнатуры) или на границах публичного API.

### 12. `Scanner.Save` ↔ `ReadJSONDevices` — несовместимые форматы

**Проблема:** `Save` пишет объект `{"devices": [...]}`, а
`ReadJSONDevices` ожидает голый массив `[...]`. Файл, записанный `Save`,
не читается обратно (в Python-оригинале `read_json` читает ключ
`["devices"]`).

**Исправление:** привести `ReadJSONDevices` к формату `{"devices": [...]}`
(заодно сохранить обратную совместимость с файлами openant).

### 13. Неограниченный рост буферов

**Проблема:** `c.burst` (`ant/node.go:222`) растёт, пока пир не пришлёт
last-флаг; `eventBuffer` (`easy/filter.go`) копит события, если их никто
не ждёт (#6/#111 в TODO). Темп роста ограничен RF-каналом — severity
низкая.

**Исправление:** ограничить оба разумными лимитами (для burst —
максимальный размер transfer; для eventBuffer — политика drop-oldest
или кап с логированием).

## P3 — мелочи (best practices)

- [ ] **`ant/node.go:160–170` и `reader()`:** сравнение ошибок через `==`
  вместо `errors.Is`. Ветка `case err == ErrBadSync` мёртвая (ParseFrame
  оборачивает через `%w`; поведение случайно совпадает с `default`).
- [ ] **Мёртвый код (staticcheck U1000):** `uint16LE` (`ant/message.go:341`),
  `eventBuffer.snapshot` (`easy/filter.go:81`).
- [ ] **`resources/42-ant-usb-sticks.rules`:** `MODE="0666"` делает
  устройство доступным всем; если цель — доступ группы `plugdev`,
  логичнее `0660`.
- [ ] **README против кода:** заявлен «Go >= 1.22», в `go.mod` — `go 1.25`;
  описан CLI `goant` (`cmd/goant`), отсутствующий в репозитории.
  Синхронизировать документацию.

## Что проверено и не требует действий

- `ParseFrame`/`ParseFrames` — корректные граничные проверки,
  ресинхронизация на bad sync/checksum.
- Все профильные парсеры страниц защищены проверкой длины; исправления
  багов openant (capabilities byte 6, `shift` page 3, CreateFile pipe,
  `controls_device` 0x47) подтверждены в коде.
- `usbDriver` — корректная синхронизация, `Close` пробуждает
  заблокированный `Read`, идемпотентный `Open`.
- Минимальные зависимости (`gousb`, `serial`); сетевые ключи публичны
  by design, задокументированы, в логах не светятся.
- Тесты зелёные с `-race`; нет `unsafe`, exec, сетевого кода.
